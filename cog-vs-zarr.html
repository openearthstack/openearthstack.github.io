Cloud Optimized GeoTIFF vs ZARR.

Two cloud-native raster formats dominate Earth observation. They solve related but different problems.

Cloud Optimized GeoTIFF (COG)

A standard GeoTIFF that has been internally tiled and contains embedded overviews (pyramid levels). Readable by any GDAL-based tool but designed to be queried partially over HTTP range requests: fetch only the bytes for a spatial subset, or a lower-resolution overview, without downloading the full file.

Strengths: near-universal tooling support, easy to serve from S3/GCS/Azure Blob, no new runtime dependencies.

Weaknesses: one file per raster per time step. Scanning a time series means many HTTP requests.

ZARR

A chunked, compressed, N-dimensional array format. Rasters live as multidimensional arrays (for example, time × band × y × x) stored as many small chunk files. Tools like xarray and dask operate on them lazily.

Strengths: cloud-native for time-series and hyperspectral cubes. Excellent for stacking thousands of acquisitions or dozens of bands into one logical array. Parallelises naturally.

Weaknesses: younger ecosystem, less universal GIS tooling, more complex to serve to non-Python clients.

When to use which

  • COG: single-scene products, tile services, interop with GIS tools, user-facing web maps.
  • ZARR: dense time-series SAR stacks, InSAR coherence cubes, multi-polarisation multi-date bundles.
  • Both: most production pipelines publish COGs as per-scene deliverables and maintain a ZARR cube for analytics.
